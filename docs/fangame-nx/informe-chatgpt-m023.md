## Controles y editor

La capa real es SDL GameController en `eventthread.cpp`, seguida de la entrada de mkxp-z/RGSS. El perfil por juego `buttonmap_<id>` guarda 15 destinos lógicos y fuentes físicas A..Q: **A/B/X/Y, MINUS, PLUS, L3/R3, L/R y cuatro direcciones de cruceta**, más **ZL/ZR** cuando SDL los presenta como ejes de gatillo. GUIDE permanece reservado. Al reasignar una fuente ocupada se intercambian las entradas; al asignar ZL/ZR se desasocia la fuente anterior del destino. Se admite la migración del antiguo `controls_<id>` de cuatro letras de b36 sin modificar el valor original. Los botones liberados se procesan con el mismo mapeo, se limpia el estado al abrir el menú o desconectar el mando, y la captura se hace sobre el botón físico. La combinación **L+R+PLUS se detecta antes del remapeo** y se conserva.

El editor del menú rápido tiene tres páginas de cinco entradas, selección de botón físico, aviso de intercambio y cancelación de captura por tiempo de espera de diez segundos. La vista de sticks permite intercambiar izquierdo/derecho, invertir X/Y de cada uno, y escoger zona muerta de 0, 4 000, 8 000 o 12 000 unidades SDL; el valor predeterminado es 8 000. Restaurar devuelve botones y sticks al perfil inicial. ZL/ZR se convierten a botón al superar un umbral fijo de 16 000, mientras el eje analógico sigue llegando al juego. Cada perfil se guarda en `config/launcher.json`; el límite de lectura se amplió de 4 a 16 KiB.

**Límites reales:** SDL GameController estándar no expone SL/SR individuales en este recorrido, y no se les asignó un código ficticio. GUIDE es del sistema. No hay todavía conversión digital de direcciones del stick a botones lógicos, curva de sensibilidad ni umbral configurable de ZL/ZR. Tampoco hay prueba física por modelo: Joy-Con individual, pareja y Pro Controller necesitan una matriz en Switch. El perfil evita colisiones entre botones, pero las opciones analógicas no se han medido dentro de un juego real.

## Releases: alcance exacto

`packaging/release_updater.py` es una herramienta **de PC** de protocolo 1. Consulta la API REST de GitHub para releases estables o beta, compara versión y build, muestra fecha/notas/asset y admite 404 como ausencia de release. Puede construir un ZIP con **solo** `switch/FangameNX/FangameNX.nro` y `manifest.json`, con destino permitido, plataforma, arquitectura, canal, tamaño y SHA-256. Verifica contenido y hash interno; al preparar una descarga exige URL bajo el repositorio configurado, `digest` SHA-256 de GitHub, tamaño exacto, espacio libre y staging temporal. No instala, no altera la Switch y no descarga fangames ni guardados. `gh api repos/theflash48/fangame-nx/releases` devolvió `[]`; la consulta real de canal estable devolvió `null`.

El paquete privado de ensayo `local/m023/FangameNX-0.2.4-b38.zip` tiene SHA-256 `dac8b649b9b0829fead6a2cf68a8ca9a5e36ba4d191eff5ebdc7e5eb5d6205d2`. El hash del NRO dentro del manifiesto coincide con el instalado. El digest servido por la API de GitHub y TLS dan comprobación de integridad respecto a GitHub, **no una firma independiente del autor**; no se encontró una dependencia Ed25519 disponible en el entorno. No se ha creado helper de sustitución del NRO en ejecución ni rollback automático, y por ello la instalación desde la propia Switch queda deshabilitada. Para publicar más adelante habrá que definir firma de manifiesto, clave pública anclada, protocolo de actualización pendiente y recuperación tras corte de energía. Documentación consultada: [API de Releases de GitHub](https://docs.github.com/en/rest/releases/releases?apiVersion=latest).
